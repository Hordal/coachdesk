# 27 소프트웨어 구조 설계
상태: 기본안. 모델·도메인 기준 없이 구현 시작 가능한 구조. 라이브러리 이름 = 후보, 구현 시 호환성 확인 후 확정.

## 1. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 단일 정의 | 14의 객체 계약 = 서버 Pydantic 모델 한 곳에서 정의. JSON Schema(2020-12)·OpenAPI는 모델에서 내보내기, 화면 타입은 OpenAPI에서 생성. 수작업 이중 정의 금지, 내보낸 파일의 최신 여부는 테스트가 확인 |
| 모델 교체 가능 | 분석 단계를 인터페이스로 분리. 구현(가상 결과·규칙·학습 모델)과 무관하게 같은 출력 형식 |
| 가상 결과로 선행 개발 | 02A 가상 예제를 결과로 읽는 실행 모드 → 모델 없이 서버·화면 개발·시험 |
| 표시 규칙의 코드화 | 19의 표시 규칙(미산출을 0으로 표시하지 않음 등)을 화면 컴포넌트가 강제 |
| 숫자·문장 = 서버 생성 | 집계·문장: 서버가 구조화된 값 + 템플릿으로 생성, 화면은 표시만(14, 19) |
| 단일 호스트로 시작 | 모듈별 서버 없음. API 서버 + 분석 워커 2개 프로세스로 시작(12, 22) |

## 2. 전체 구성

| 구성 요소 | 역할 | 기본안 |
|---|---|---|
| 웹 화면 | 업로드, 선수 지정, 진행 확인, 결과 열람, 장면 복기, 정정·삭제 | TypeScript, React, Vite |
| API 서버 | 인증·권한, 요청 검증, 조회, 작업 생성, 서명된 파일 접근 | Python, FastAPI |
| 분석 워커 | 작업 큐에서 작업을 받아 분석 단계를 순서대로 실행 | 별도 프로세스, 초기 1개(13) |
| 메타데이터 저장소 | 사용자, 영상, 작업, 사건급 결과, 정정 | SQLite |
| 시계열 저장소 | 프레임별 관측(관절, 측정값) | Parquet 파일 |
| 파일 저장소 | 원본·재생본·프레임 이미지·근거 클립 | 비공개 로컬 디렉터리, DB에는 참조만 저장 |

흐름: 웹 화면 → API 서버 → SQLite 작업 테이블 → 분석 워커 → 저장소 → API 서버 → 웹 화면

## 3. 백엔드

### 3.1 디렉터리 구조

✓ = 구현됨, 빈칸 = 계획만.

```
backend/
  app/
    api/                  요청 처리(라우터), 오류 응답 변환, 의존성(인증·소유자 확인)
      v1/                 runs ✓  videos ✓  uploads ✓  corrections ✓  observations ✓  auth ✓  views ✓
      errors ✓  deps ✓  schemas ✓  main ✓  asgi ✓
    domain/               14의 객체와 규칙. 웹 프레임워크·저장 방식을 알지 않음
      models ✓            결과 객체, 선수 검출·추적·포즈 형식, 가져오기 입력(단일 정의)
      aggregation ✓       판정에서 집계를 다시 계산
      contract_check ✓    참조·시간·판정·집계·보류 규칙 검사
      findings ✓  labels ✓  템플릿 문장 생성, 문장에 쓰는 한국어 표기
    pipeline/             분석 단계
      stages ✓  registry ✓  단계 인터페이스 12개, 실행 모드
      impl/fixture ✓      가상 예제 공급(rules·models는 아직 없음. manual 실행은 services/imports가 맡음)
    jobs/                 store ✓ 작업 큐·소유권·lease  ingest ✓ 영상 준비 단계  runner ✓ FFmpeg  worker ✓ 워커
    services/             uploads ✓  imports ✓  observations ✓  designation ✓  corrections ✓  deletion ✓
    storage/              db ✓ SQLite·마이그레이션  videos ✓  memory ✓ 실행 결과 저장소
    media/                probe ✓ FFprobe·프레임 표  admission ✓ 입장 검사  store ✓ 파일·서명 주소  binaries ✓
    auth/                 service ✓ 초대·세션·로그인 제한·감사  cli ✓ 첫 관리자 만들기
    settings ✓            설정과 한도값
  schemas/ ✓              result_bundle, manual_import, observations, openapi (모델에서 내보냄)
  scripts/ ✓              export_schema, make_demo_media
  tests/ ✓                서버 시험과 팀 파이프라인 실제 출력 일부(tests/fixtures)
  data/                   실행 중 생기는 DB·원본·재생용 사본·가져온 결과(저장소에 포함하지 않음)
```

- 의존 방향: api → domain ← pipeline, jobs → pipeline·storage
- domain: 웹 프레임워크·저장 방식 비의존, Pydantic은 데이터 모델 정의에만 사용
- 검사 도구 `tools/contract_check` = domain 검사 모듈 호출 진입점

### 3.2 분석 단계 인터페이스

14의 공통 작업 요청·응답 형식 준수. 모든 단계: 입력 참조 + 설정 입력 → 출력 참조·상태·경고·오류 반환.

| 단계 | 입력 | 출력 | 구현 종류(1단계) |
|---|---|---|---|
| VideoReader | 원본 영상 | Frame, 시간 대응 | FFmpeg·FFprobe |
| Detector | Frame | 검출 프레임(timestamp_us, detections[bbox_xyxy, score]) | 모델(교체 가능) |
| Tracker | 검출 프레임 | 추적 프레임(timestamp_us, tracks[track_id, bbox_xyxy, tracking_score]) | 모델·알고리즘 |
| AssignmentResolver | 추적 프레임, 선수 지정 | TrackAssignment(NOT_RUN/ASSIGNED) | 사용자 입력(구현됨) |
| PoseEstimator | Frame, 선수 영역 | Pose(관절) | 모델(교체 가능) |
| MetricCalculator | Pose, 보정 정보 | MetricSample(Feature, 거리) | 규칙(25, 26) |
| StateJudge | MetricSample | StateInterval | 설정 규칙 엔진(25) |
| ActionClassifier | Pose, MetricSample | Event(action) | 규칙 기준선, 학습 모델(24) |
| ContactJudge | Event, Pose, 선택적으로 영상 | Assessment(접촉), Event(contact) | 규칙 기준선, 영상 모델(24) |
| RelationLinker | Event | EventRelation, Exchange | 규칙(시간적 후속 공격) |
| Aggregator | Event, Assessment, 관계 | Aggregate | 규칙 |
| FindingBuilder | Aggregate, Assessment | Finding | 템플릿 |

단계별 구현 선택: 설정(`registry.py`). 같은 단계에 구현 복수 가능, 실행된 구현·버전은 AnalysisRun에 기록(16).

### 3.3 실행 모드

| 모드 | 사용하는 단계 | 용도 |
|---|---|---|
| fixture | 모든 단계를 가상 예제 JSON으로 대체 | 화면·API 개발, 시연, 회귀 테스트 |
| manual | 사람이 입력한 사건·판정(스키마 준수 JSON 또는 라벨링 도구 내보내기)을 입력으로, Aggregator와 FindingBuilder만 실행 | 모델 없이 파일럿, 라벨 검수, 집계 로직 검증 |
| partial | 완성된 단계는 실제 구현, 나머지는 manual 입력 사용 | 단계별 모델 성능 평가, 점진적 교체 |
| full | 모든 단계가 실제 구현 | 목표 구성 |

fixture 모드: 영상 없이 결과만 제공 → 근거 영상 `unavailable` 표시. 화면 시험 시 임의 시험 영상 연결.

### 3.4 저장 구조

| 저장 대상 | 저장소 | 상태 |
|---|---|---|
| 업로드, 영상, 작업과 작업 이력, 실행(결과 묶음 전체) | SQLite(`uploads`, `upload_parts`, `videos`, `jobs`, `job_events`, `runs`) | 구현. 실행의 결과 묶음은 JSON으로 한 행에 저장 |
| 정정, 신고, 의도 설명 | SQLite(`corrections`, `reports`, `context_notes`) | 구현 |
| 사용자, 초대, 세션, 로그인 시도, 감사 기록 | SQLite(`users`, `invites`, `sessions`, `login_attempts`, `audit_log`) | 구현. 토큰은 해시만 저장 |
| 가져온 검출·추적 결과 | 요약은 SQLite(`observation_sets`), 프레임별 내용은 `data/observations/{video_id}/{set_id}.json` | 구현. 대량 시계열 형식(Parquet): 실제 규모 측정 후 결정 |
| 선수 지정 | SQLite(`designations`). 바꾸면 새 행을 추가하고 이전 행은 이력으로 남김 | 구현 |
| 원본·재생용 사본 | `data/originals/{video_id}`, `data/media/{video_id}.mp4`. DB에는 상태와 체크섬만 | 구현 |
| 사건급 결과를 객체별 테이블로 분리 | 미실시. 가져온 결과 규모 실측 전에는 결과 묶음 JSON으로 충분 | 미정 |
| 프레임별 관절(PoseSet) | 개발용 JSON 파일 | 실제 포즈 모델 연결 시 결정 |

- 테이블 관계: Video 1—N AnalysisRun. 정정 시 새 AnalysisRun 생성 + `parent_run_id` 연결(16)
- 스키마: 번호 있는 마이그레이션(현재 6번)으로 상승, 이전 번호 수정 금지
- 영상 삭제: 15의 절차에 따라 원본·파생 파일·DB 행 일괄 정리

### 3.5 작업 처리

12의 규칙 준수.
- 워커: SQLite 작업 테이블에서 소유권(lease) 획득, 단계마다 진행량·heartbeat 기록
- 단계 완료 시 체크포인트 → 중단 후 마지막 완성 단계부터 재개
- 취소: 플래그 확인, 미완성 출력 미등록
- 중복 제출: Idempotency-Key로 작업 하나만 생성

### 3.6 API

- 경로 `/api/v1`. 요청·응답 UTF-8 JSON, 오류 RFC 9457 Problem Details(14)
- 모든 요청에서 서버가 소유자·권한 검사(21)

| 영역 | 메서드·경로 | 설명 | 상태 |
|---|---|---|---|
| 인증 | GET·POST /auth/invites/{token}, POST …/accept | 초대 확인과 수락(동의 필수) | 구현 |
| | POST /auth/login, POST /auth/logout, GET /me | 세션. /me가 CSRF 토큰을 줌 | 구현 |
| 운영 | POST·GET /admin/invites, DELETE /admin/invites/{id}, GET /admin/users, POST /admin/users/{id}/block·unblock | 초대, 계정 차단 | 구현 |
| 업로드 | POST /uploads, PUT /uploads/{id}/parts/{n}, GET·DELETE /uploads/{id}, POST /uploads/{id}/complete | 분할·재개 가능. Idempotency-Key 필수. 완료 때 내용 검증 후 영상과 작업 생성 | 구현 |
| 작업 | GET /jobs/{id}, POST /jobs/{id}/cancel | 단계별 진행, 취소 | 구현 |
| 영상 | GET /videos, GET /videos/{id}/summary, GET /videos/{id}/playback | 목록, 상태와 작업 진행, 영상 전체 재생 주소 | 구현 |
| | GET /videos/{id}, GET /videos/{id}/frames, GET /videos/{id}/frame-image | 영상 정보, 실제 프레임 시각 표, 디코더가 식별한 정지 프레임 | 구현 |
| | GET /media/{video_id}?exp=&sig= | 서명된 주소로만 영상 제공(범위 요청 지원) | 구현 |
| | DELETE /videos/{id}, DELETE /videos/{id}/media | 영상과 결과 전체 삭제, 원본·재생용 사본만 삭제 | 구현 |

| 선수 지정 | GET /videos/{id}/designation-frames | 후보 프레임과 표시 좌표의 트랙 상자 | 구현 |
| | GET·PUT /videos/{id}/designation | 사용자가 USER·OPPONENT 트랙을 직접 선택 | 구현 |
| 결과 | GET /runs, GET /runs/{id} | 실행 목록, 요약(정정 관계 포함) | 구현 |
| | GET /runs/{id}/findings, …/aggregates/{aid}, …/timeline, …/events/{eid} | 주장·집계·타임라인·사건 상세 | 구현 |
| 근거 | GET /runs/{id}/evidence, …/evidence/{evid}, …/poses | 근거 구간과 재생 주소, 관절 관측(표시 좌표) | 구현 |
| 정정 | POST /runs/{id}/corrections/preview, POST·GET /runs/{id}/corrections | 본인 지정 정정(새 실행), 이력 | 구현. 선수 연결·라운드 경계 정정은 아직 |
| | POST·GET /runs/{id}/reports, POST·GET /runs/{id}/context-notes | 오류 신고, 의도 설명(self_report) | 구현 |
| 분석 | POST /videos/{id}/runs, POST /runs/{id}/cancel | 분석 실행 요청·취소(모드·설정) | 아직 |

결과 조회 응답: 객체의 status·reason_code 그대로 포함. 미산출 값 = null, 서버의 0 대체 금지.

### 3.7 문장 생성

- FindingBuilder: Aggregate·Assessment의 구조화된 값 → 템플릿 문장
- 응답 구성: `template_id`, 문장에 쓰인 값(`slots`), 렌더링된 문장, 근거 참조
- 근거 부족한 원인·교정 주장: `status=withheld` + 보류 사유, 화면이 사유 표시
- 문장의 숫자·시각: 출력 전 원자료와 대조(19)

### 3.8 보안과 한도

- 세션: TLS, 안전한 쿠키, 만료, CSRF 보호
- 파일: 공개 경로 배치 금지, 서명 URL로만 접근
- 업로드 크기·길이·픽셀 수·가용 디스크: 입장 검사에서 확인(13)
- 한도 값 전부 임시 값, 10절에 정리. 영상 규격·최대 길이 결정(30의 P04·T06): 13. 영상 준비 시간 실측: 9절
- 로그에 원본 프레임·토큰·서명 URL·실명 기록 금지(17)

## 4. 프론트엔드

### 4.1 화면

01의 사용 흐름 6단계 대응.

| 화면 | 사용자 행동 | 표시 내용 |
|---|---|---|
| 초대 수락·로그인 | 초대 링크로 계정 생성, 로그인 | 이용 안내, 영상 이용 동의 항목 |
| 영상 목록 | 영상 선택, 새 업로드 | 영상별 분석 상태(대기·진행·완료·부분 완료·실패), 원본 만료일 |
| 업로드 | 영상 선택, 종목·선수 정보 입력 | 형식·품질 검사 결과, 권장 촬영 조건 대비 부족한 항목, 업로드 진행·재개 |
| 선수 지정 | 두 선수가 보이는 프레임에서 본인 선택 | 후보 프레임 탐색, 선택한 선수 확인 |
| 분석 진행 | 진행 확인, 취소 | 단계명, 처리 구간 기준 진행률. 근거 없는 완료 예정 시간 없음 |
| 결과 요약 | 발견 사항 선택 | 주요 장면, 반복 문제·강점, 판단 불가, 관찰·집계·원인·교정 영역 분리, 교정 미제공 표시 |
| 집계 상세 | 숫자 근거 확인 | 확인된 전체 → 판정 가능 → 발생 → 판단 불가·제외 구성과 해당 사건 목록 |
| 장면 복기 | 구간 재생, 사건 이동 | 영상, 선수·관절 오버레이, 타임라인(상태 구간·행동 사건·접촉), 사건 상세 |
| 정정·신고 | 선수 연결 정정, 오류 신고, 의도 설명 | 적용 구간·재계산 영향 미리 보기, 정정 이력, 최초 결과 보존 표시 |
| 설정·삭제 | 영상·결과 삭제 | 보관 정책 안내, 삭제 진행 상태, 원본 만료 후 근거 재생 불가 안내 |

체육관에서 태블릿·휴대폰 열람 → 모든 화면 휴대폰 너비 사용 가능. 장면 복기: 영상·타임라인 세로 배치.

### 4.2 표시 규칙 컴포넌트(19)

| 컴포넌트 | 규칙 |
|---|---|
| DataValue | null → '확인 불가' + 사유 표시, 0 표시 금지 |
| StatusBadge | 있음·없음·판단 불가·해당 없음을 색 + 텍스트·아이콘으로 구별, 색 단독 구별 금지 |
| CountBreakdown | 확인된 전체·판정 가능·발생·판단 불가·제외 동시 표시. 분모 0 → '비율 없음' |
| TimelineTrack | 값 없는 구간 = 공백, 0으로 이어 그리기 금지. 보간·추정 구간 = 선 스타일·문구로 구별 |
| FindingCard | 관찰·집계, 원인 가설, 교정 방향 = 별도 영역. 보류된 주장 = 사유와 함께 표시, 숨김 금지 |
| EvidenceLink | 클릭 시 해당 구간 이동. 원본 만료 시 구조화된 근거 표시 + 재생 불가 표시 |
| ExpiredNotice | 원본 삭제 후 근거 재생·재계산 불가를 일관된 문구로 표시 |

백분율 정확도·근거 없는 오차 범위 표시 컴포넌트 제작 금지.

### 4.3 영상 재생과 시간 동기화(05)

- 재생 위치 이동: `currentTime` 사용, `seeked` 이후 실제 표시 확인. 정밀 이동에 `fastSeek` 금지
- 지원 브라우저: `requestVideoFrameCallback`의 `mediaTime`으로 표시 프레임 시각 확인 → 오버레이 정렬
- 목표 시점 1프레임 이내 불일치 또는 확인 불가 시: 서버 제공 정지 프레임 이미지(프레임 ID·시각·좌표 포함)로 전환
- 오버레이: 원본 시각 기준 데이터(`time_us`) 그대로 사용, 화면 좌표만 영상 크기에 맞게 변환

구현 확인 사항(2026-10-05)
- 브라우저는 영상 파일의 프레임 길이 정보에 따라 ffprobe가 읽은 프레임을 건너뛸 수 있음. 가변 프레임률 시험 영상에서 일부 프레임(5개 중 1개꼴) 미표시, 디코더(ffmpeg)는 정상 출력. 구현 규칙: 이동 후 목표 프레임 표시 확인, 미표시 시 정지 프레임 전환(0.5초 내 미표시 시 전환, 사용자 안내)
- 프레임 시각 표: 구간 시작 1초 전부터 수신. 이유: 브라우저가 구간 시작 프레임을 건너뛰고 직전 프레임을 표시할 수 있음
- 표시 시각 그대로 탐색 시 반올림으로 이전 프레임 표시 가능 → 목표 프레임·다음 프레임 중간 지점으로 탐색
- 사건 이동: 사건 시작 이후 첫 프레임으로 이동. 시작 시각에 보이던 프레임이 사건 시작보다 앞설 수 있음
- 재생이 구간 끝에 도달: 정지 후 구간 마지막 프레임으로 복귀. 프레임 표 밖 프레임의 마지막 프레임 표기 금지
- 프레임 표·관절: 60초 이하 구간에서만 수신. 더 긴 구간: 영상 재생 + 타임라인만 제공
- 측정: 고정 프레임률 영상 41프레임, 가변 프레임률 영상 20프레임(정지 프레임 전환 5개 포함) → 영상 속 도형 중심과 오버레이 중심 차이 최대 2.0px(평균 약 1px). 도형 이동 프레임당 약 9~13px → 1프레임 어긋남 구별 가능

- 영상 규격: 720p·30fps 이상 기본 지원, 1080p·60fps 권장. 최대 길이: 서버 성능 실측 후 결정. 서버는 규격 미만 영상을 거절하지 않고 영상 준비 결과에 충족 여부 표시
- `cfr_timestamp_us` = 고정 프레임률 시험용 보조 함수, 분석 기준 = 원본 PTS
- 현재 `bbox`·`confidence` 파일 형식 = 실험용 산출물 → `bbox_xyxy`·`score`·`tracking_score`·`timestamp_us`로 통일 예정. 서버: 기준 이름을 JSON Schema·API 명세에 사용, 실험용 이름도 함께 수신, 프레임 번호 필드 없으면 줄 순서 사용
- 방식: 파이프라인이 표준 JSON·JSONL 생성 → 서버가 가져오기
- 키포인트 = (x, y, confidence), z 미사용
- RT-DETR R18 = 프로토타입 기준 모델, 제품 검출 모델은 검토 후 결정

필요 자료: 다른 영상의 파이프라인 출력(가려짐 많은 장면, 오래 겹치는 장면, 다른 해상도·프레임률의 `metadata.json`·`tracking_frames.jsonl`·`tracking_diagnostics.json`) → 가져오기 시험 확대. 현재 영상 1개 출력으로만 시험.

연동 순서

1. 위 계약 정렬(선수–트랙 배정 저장 제외, 완료)
2. `metadata.json`·`tracking_frames.jsonl`·`detection_frames.jsonl`(선택) 읽기 전용 가져오기(완료)
   - 프레임 수·모든 프레임 시각이 영상 프레임 표와 불일치 시 가져오기 거부
   - 분석 영상 프레임 수 ≠ 원본 PTS 수 시 거부(프레임 번호로 시각 정렬 불가)
   - 기준 표: 분석 파이프라인이 읽은 원본 영상의 프레임 시각(반올림 차이 2µs 허용). 원본 없을 때: 재생용 사본 표 사용, 영상 준비 단계 확인 한도(1ms) 허용. 시작 시각이 옮겨진 상수 차이: 허용
   - 검출 프레임: 크기 = 분석 프레임(변환 정보의 analysis 크기), coordinate_space = analysis_frame_xyxy_px 필수
   - 같은 내용 재가져오기: 신규 생성 없음. 분석 컴퓨터 로컬 경로 미저장
   - 가져온 트랙 = 후보일 뿐, 선수 배정 NOT_RUN
3. 후보 프레임 제시(`GET /videos/{id}/designation-frames`) + 선수 지정(`GET·PUT /videos/{id}/designation`) API, 대표 프레임 위 후보 상자 선택 화면(완료)
4. 검출·추적 구현의 워커 `detector`·`tracker` 단계 편입(partial 모드)
5. 포즈 단계(상업 이용 가능한 가중치 확인 후)

선수 지정 단계 구현(2026-10-06)
- 후보 프레임 선정: 오래 보이고 화면에서 큰 트랙 2개(보인 프레임 수 × 면적 중앙값)가 함께 보이며 서로 겹치지 않는 프레임 최대 5개. 해당 프레임 없음 → 겹친 장면 표시 + 안내. 이 기준 = 표시 프레임 선정용, 신원 판정 아님
- 상자: 표시 영상 좌표로 변환해 응답. 프레임 이미지: 기존 `frame-image` 사용

- 서버 거절 대상: 존재하지 않는 트랙 번호, 한 트랙의 양쪽 지정, 같은 선수로 고른 트랙이 같은 프레임에 동시 출현하는 모순
- 같은 선택 재전송: 이력 증가 없음. 변경 시 이력 보존. 검출·추적 결과 재가져오기 시 지정이 `NOT_RUN`으로 복귀, 이전 결과 기준 선택은 409로 거절
